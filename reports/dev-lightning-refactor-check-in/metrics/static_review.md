# Static review of de0f5ee..origin/dev (4 lenses, 3 adversarial refuters per finding, 110 agents)

## Static review: de0f5ee → origin/dev (0b90790), effect on multitask-eval AUROCs

**Old code:** `.claude/worktrees/old-eval-baseline`; **new:** `.claude/worktrees/dev-lightning-refactor-check-in`. Model, dataset, collate, loader parent and checkpoint loader are byte-identical in the range: `src/every_query/model/conditional_multitask_ar_model.py`, `src/every_query/data/multitask_eval_dataset.py`, `src/every_query/data/seq_dataset.py`, `src/every_query/data/datamodule.py`, `src/every_query/utils/model_loader.py`, `src/every_query/model/lightning_module.py`, `src/every_query/train/train.py`.

### 1. Changes that can move the numbers (in order of importance)

1. **Inference precision default `bf16-mixed`** (`src/every_query/predict/predict_multitask.py:338` `DEFAULT_PREDICT_PRECISION`, `predict_multitask.yaml:62`). This is the *only* change in the diff that alters a probability. Lightning wraps `predict_step` in `torch.autocast(bfloat16)`, so everything inside `window_hidden_states` (duration MLPs, window-token assembly, every Linear, SDPA) runs in bf16; RMSNorm, the fp32 residual, the `autocast(enabled=False)` scoring head in `score_final_query` and `torch.sigmoid` stay fp32. Expected: |Δprob| ~1e-2 per row (test tolerance 2e-2 on the toy model, `tests/test_conditional_multitask_cli.py:414`; a few rows on the 12-layer production backbone may exceed that). Per-task AUROC: typically <1e-3 on tasks with hundreds of rows; up to ~1e-2 on tiny tasks / few positives where near-tied rows re-rank. `precision=32-true` makes the autocast context a no-op and reproduces the old numerics.
2. Nothing else. Every other change was verified computation-neutral for `EQ_predict_multitask` (section 2), and the training-side changes reproduce the old trajectory (a retrain differs only by ordinary GPU nondeterminism).

### 2. Verified same computation (old manual loop vs `Trainer.predict`)

- **Dataset**: same `instantiate(datamodule.config, task_labels_dir=tasks_dir)`; `eval_config = dataclasses.replace(...)` in `src/every_query/data/conditional_multitask_datamodule.py` re-runs an idempotent `__post_init__` and is field-for-field equal. `QuerySeqMultitaskEvalDataset` gets the same `split`, `strip_delta_tokens`, `expected_vocab_size`, `max_windows`; same whole-run rejections; no per-row filtering.
- **Row order / batching**: CLI `batch_size=192` and checkpoint `num_workers=8` reach the loader on both sides; `BatchSampler(SequentialSampler, 192, drop_last=False)` on both. Lightning's predict rewrap only inserts a pass-through `_IndexBatchSamplerWrapper`, so batch membership, hence per-batch pad widths K and S, hence model inputs, are identical. New loader kwargs `pin_memory=True` / `persistent_workers=True` and Lightning's `worker_init_fn` are inert: the batch is a plain dataclass (never pinned), predict iterates once, and the TO_END eval path consumes no RNG.
- **Device transfer**: `move_data_to_device` moves every tensor field of `MultitaskEvalBatch` with `non_blocking=True`, no `__post_init__` re-run, no dtype change — same as the removed `_to_device`.
- **Forward**: same `score_final_query(batch, batch.scored_codes)`, `eval()` mode in both (no stochastic layers anyway), `inference_mode` vs `no_grad` arithmetic-neutral, `set_float32_matmul_precision("high")` still set by the unchanged `setup_model` before the Trainer exists; Lightning writes no torch backend flags.
- **Output**: fp32 logits → fp32 sigmoid on both sides; `torch.cat` vs `np.concatenate` bitwise equal; `predictions_to_df` frame assembly is byte-identical (columns, dtypes, window-list defaults, row order). The added `scored_codes` alignment check can only raise, never re-order.
- **Training / checkpoint**: `ConditionalMultitaskDataModule` pins `data_class=MultitaskBoundaryPytorchDataset` and inherits train/val datasets and loaders unchanged; the new explicit `validation_step` + 3-arg `_log_metrics` issue the same `tuning/loss` `self.log` call the inherited path did, so checkpoint selection / early stopping are unchanged. Datamodule hparams gain four keys that nothing reads on load. `build_predict_datamodule` never reads `_target_`/`data_class`, so the pre-#30 checkpoint resolves identically.

### 3. What to expect from the empirical runs

- **Old code re-run vs stored baseline**: bitwise equal on the same GPU/driver/torch (same kernels, same shapes, deterministic-in-practice cuBLAS/SDPA). Any nonzero diff here is the machine's noise floor, not a code effect.
- **Dev code `precision=32-true` vs stored**: expected bitwise equal on the same hardware — same fp32-weights + TF32-GEMM kernels, same padded shapes, same row order. A diff at ≤1e-6 would mean kernel nondeterminism (compare against the old-code re-run diff); anything larger points at a batch-composition difference (e.g. a different `batch_size` between runs changes pad widths and gives ~1e-6–1e-5, at most 1e-4, in prob) or a different device. Note "fp32 baseline" is really fp32+TF32 (`matmul_precision high`), on both sides.
- **Dev code default (`bf16-mixed`) vs stored**: max |Δprob| ~1e-2 (some rows possibly a bit above 2e-2); `label`, `target_code`, window columns and row order identical; per-task AUROC Δ typically <1e-3, larger only on tiny tasks. This delta should equal (dev bf16 − dev 32-true) to within the noise floor; if it does not, the plumbing, not autocast, is responsible.

### 4. Bugs / doc nits worth fixing

- `tests/test_conditional_multitask_cli.py:363-379` (`test_predict_multitask_accepts_a_pre_issue_30_run_dir`): the docstring reads as old-vs-new, but it compares two runs of the *new* CLI (rewritten datamodule node vs native). - Behavioural change outside the eval suite, by config not code: `do_resume=true` on a pre-#30 run dir is now refused by `src/every_query/train/resume_check.py` (`datamodule._target_`, `data_class`, `eval_tasks_dir`, `max_windows` are not in `ALLOWED_DIFFERENCE_KEYS`). ## Confirmed findings (survived 2/3 adversarial refuters)

### bf16-mixed autocast now wraps the backbone pass (known change; mechanism and scope pinned down)

- file: `src/every_query/predict/predict_multitask.py` (lens: inference-numerics, affects: probabilities, expected: ~1e-2 absolute in prob (bf16 rounding through 12 layers); per-task AUROC typically <1e-3 on tasks with hundreds+ rows, up to ~1e-2 on tiny tasks where near-tied rows can reorder; 32-true should be bitwise identical to the old loop, confidence: high)

Old: `@torch.no_grad() def run_inference(...)` called `logits = model.model.score_final_query(batch, batch.scored_codes)` with no autocast at all, fp32 weights, matmul precision 'high'. New: `Trainer(precision=precision, ...)` with `DEFAULT_PREDICT_PRECISION = "bf16-mixed"`; Lightning's `Strategy.predict_step` runs `predict_step` inside `MixedPrecision.forward_context()` = `torch.autocast('cuda', dtype=torch.bfloat16, cache_enabled=False)`. Inside `score_final_query` (unchanged file) only the final projection is explicitly protected: `with torch.autocast(device_type=selected.device.type, enabled=False): rows = embedding_weight[scored_codes].float(); logits = (selected.float() * rows).sum(dim=-1) + self.code_bias[scored_codes].float()`. Everything before it — the duration MLPs in `_query_tokens`, every q/k/v/o and MLP Linear inside `self.HF_model(...)`, and SDPA attention — now executes in bf16 (Linear/matmul are on the autocast lower-precision list); embedding lookups, the fp32 residual stream (inputs_embeds is fp32, so residual adds promote back to fp32), RMSNorm internals and the RoPE cos/sin remain fp32. `torch.sigmoid` is not on any autocast cast list, so `torch.sigmoid(logits)` on the fp32 logits stays fp32 in both paths. Passing `precision=32-true` makes `Precision.forward_context` a null context, i.e. the exact old numerics.

### inference_mode + Lightning eval() replace no_grad + manual .eval(): no numeric effect

- file: `src/every_query/predict/predict_multitask.py` (lens: inference-numerics, affects: none, expected: none / bitwise identical, confidence: high)

Old: `@torch.no_grad()` on `run_inference` and `model = model.to(device).eval()`. New: `Trainer(..., inference_mode=True)` so `_PredictionLoop.run` is wrapped by `_no_grad_context` -> `torch.inference_mode`, plus `predict_step` still carries `@torch.no_grad()`; `_on_predict_model_eval` -> `on_predict_model_eval` calls `.eval()` on the module before the loop and `model_to_device()` moves it. inference_mode only changes autograd bookkeeping (no version counters / grad tracking), never kernel selection or arithmetic. The model has no stochastic layers to be affected by eval mode anyway: `attention_dropout: 0.0`, `MLP(layers=[1, 64, H], dropout_prob=0)` for both duration MLPs, and LlamaModel has no hidden dropout.

### Lightning batch transfer moves every tensor field of MultitaskEvalBatch exactly as the old _to_device did

- file: `src/every_query/model/conditional_multitask_lightning.py` (lens: inference-numerics, affects: none, expected: none / bitwise identical, confidence: high)

Old: `_to_device` iterated `fields(batch)` and did `setattr(batch, f.name, v.to(device, non_blocking=True))` in place. New: `Strategy.batch_to_device` -> `LightningModule._apply_batch_transfer_handler` -> default `transfer_batch_to_device` -> `move_data_to_device`, whose dataclass branch (lightning_utilities 0.15.3 `apply_to_collection`) deep-copies the instance with tensors memoised (so `__post_init__` is NOT re-run and no tensor is duplicated) and then `setattr(result, field_name, v)` for every `field.init` field, retaining `None` values as `None`. All 11 extra fields of `MultitaskEvalBatch` (`q_start_durations … n_queries, time_pos_ids`) are ordinary `init=True` dataclass fields with default `None`, so `code`, `q_*`, `condition_*`, `scored_codes`, `labels`, `n_queries`, `time_pos_ids` all land on the accelerator, `non_blocking=True` for CUDA just as before. `predict_step` then returns `batch.labels.detach().cpu()` / `batch.scored_codes.detach().cpu()`. Nothing is left on CPU; and `score_final_query` already does `last_real_window(batch.q_mask).to(window_hidden.device)` as a belt-and-braces. Row order inside a batch is untouched.

### float32 matmul precision 'high' is unchanged and the Trainer does not touch torch backend flags

- file: `src/every_query/utils/model_loader.py` (lens: inference-numerics, affects: none, expected: none / bitwise identical (for 32-true); no additional contribution under bf16-mixed, confidence: high)

`model_loader.py` is byte-identical in the range: `torch.set_float32_matmul_precision("high")` still runs inside `setup_model`, which `main` calls before `build_predict_trainer`. Lightning's `_AcceleratorConnector._set_torch_flags(deterministic=None, benchmark=None)` guards every write with `if benchmark is not None` / `isinstance(deterministic, bool)`, so `cudnn.benchmark`, `use_deterministic_algorithms` and the matmul precision are all left as the old loop had them. Under `precision=32-true` the TF32-'high' fp32 matmuls are therefore the same kernels as before; under bf16-mixed the setting is moot for the bf16 GEMMs and still applies to the fp32 projection.

### seed_everything(workers=True) now attaches Lightning's worker_init_fn to the predict loader; dataset is RNG-free

- file: `src/every_query/data/conditional_multitask_datamodule.py` (lens: inference-numerics, affects: none, expected: none / bitwise identical, confidence: high)

Both paths call `seed_everything(seed, workers=True)` in `setup_model`, which exports `PL_SEED_WORKERS=1`. The old plain `DataLoader(dataset, ..., num_workers=8)` used torch's default per-worker seeding; the new loader passes through `_process_dataloader` -> `_auto_add_worker_init_fn`, which sets `dataloader.worker_init_fn = partial(pl_worker_init_function, rank=...)` because `worker_init_fn is None`. This only changes the RNG state inside DataLoader workers. `QuerySeqMultitaskEvalDataset.__getitem__` -> `MEDSPytorchDataset._seeded_getitem(idx)` with `rng=None`, and `MEDSTorchDataConfig.__post_init__` forces `seq_sampling_strategy == TO_END` whenever `task_labels_dir` is set; `SubsequenceSamplingStrategy.subsample_st_offset(TO_END, ...)` is a deterministic `seq_len - max_seq_len` offset (doc: `subsample_st_offset(TO_END, 10, 5)` -> 5, `rng` only used by RANDOM/BALANCED_RANDOM). No sample depends on worker RNG.

### Lightning re-instantiates the predict DataLoader with an index-tracking batch sampler; batches and order are unchanged

- file: `src/every_query/data/conditional_multitask_datamodule.py` (lens: inference-numerics, affects: none, expected: none / bitwise identical, confidence: high)

New `_eval_dataloader`: `DataLoader(dataset, shuffle=False, collate_fn=dataset.collate, **self.shared_dataloader_kwargs)` where `shared_dataloader_kwargs` = `{'batch_size': 192, 'num_workers': 8, 'pin_memory': True, 'persistent_workers': True}` (pin_memory/persistent_workers are new relative to the old `DataLoader(dataset, batch_size=int(batch_size), shuffle=False, collate_fn=dataset.collate, num_workers=int(num_workers))`). Lightning's `_prepare_dataloader` then hits `or mode == RunningStage.PREDICTING` and calls `_update_dataloader`, which re-creates the DataLoader from its own init args (same `batch_size`, `drop_last=False`, `collate_fn`) with `BatchSampler(SequentialSampler)` wrapped in `_IndexBatchSamplerWrapper`, whose `__next__` is `batch = next(self._iterator)` — a pure pass-through that only records indices. Same 192-row batches -> same per-batch pad widths `K` and `S` -> identical inputs to the model. `pin_memory=True` is a no-op on the dataclass batch (no `pin_memory` method, not a Sequence/Mapping) and would not change values regardless. Old-style sequential order is additionally verified after the fact by the strengthened `predictions_to_df` (labels AND `scored_codes` vs `answers[-1]` / `code_to_index[queries[-1]]`).

### eval_config via dataclasses.replace produces the same MEDSTorchDataConfig the old instantiate call did

- file: `src/every_query/data/conditional_multitask_datamodule.py` (lens: inference-numerics, affects: none, expected: none / bitwise identical, confidence: high)

Old: `data_cfg = instantiate(train_cfg.datamodule.config, task_labels_dir=str(tasks_dir))` fed straight to `QuerySeqMultitaskEvalDataset(data_cfg, split=split, strip_delta_tokens=..., expected_vocab_size=int(expected_vocab_size), max_windows=max_windows)`. ### Training path: new validation_step/training_step reproduce the parent's loss + logging exactly; datamodule swap keeps the same train/val loaders

- file: `src/every_query/model/conditional_multitask_lightning.py` (lens: inference-numerics, affects: training, expected: none beyond run-to-run nondeterminism; same batches, same objective, same checkpoint selection, confidence: high)

Old module had no `validation_step`, so training used the parent's `@torch.no_grad() def validation_step(self, batch): loss, outputs = self.model(batch); self._log_metrics(loss, outputs, batch, tuning_split); return loss`. New: `@torch.no_grad() def validation_step(self, batch): loss, _ = self.model(batch); self._log_metrics(loss, batch, tuning_split); return loss`, and `_log_metrics` logs the same `f"{split}/loss"` with identical `on_step=is_train, on_epoch=True, prog_bar=True, batch_size=batch.batch_size, sync_dist=...`. `training_step` changed only `loss, outputs` -> `loss, _`. So `tuning/loss` (the ModelCheckpoint / EarlyStopping monitor) is computed and aggregated identically. Config `_target_` moved from `ResumableDatamodule` + `data_class: ...MultitaskBoundaryPytorchDataset` to `ConditionalMultitaskDataModule`, which calls `super().__init__(config, data_class=MultitaskBoundaryPytorchDataset, batch_size=..., num_workers=..., pin_memory=..., dataset_kwargs=...)` and inherits `train_dataloader` (StatefulDataLoader, shuffle=True) and the upstream `val_dataloader` over `ResumableDatamodule.val_dataset` unchanged; `eval_tasks_dir: null` / `max_windows` / `predict_split` only land in `save_hyperparameters`. The added `hydra ... exclude_keys: datamodule.eval_tasks_dir` only affects run-dir naming. A retrain would differ from an old retrain only by ordinary GPU nondeterminism, not by any code-path change.

### Output assembly: probs concatenated via torch.cat instead of np.concatenate, same float32 values

- file: `src/every_query/predict/predict_multitask.py` (lens: inference-numerics, affects: none, expected: none / bitwise identical, confidence: high)

Old: `probs_out.append(torch.sigmoid(logits).float().cpu().numpy())` ... `np.concatenate(probs_out).astype(np.float32)`. New: `predict_step` returns `torch.sigmoid(logits).detach().cpu()` (fp32, since logits are fp32 from inside `autocast(enabled=False)`), `run_inference` does `torch.cat([out['probs'] for out in outputs]).float().cpu().numpy().astype(np.float32, copy=False)`; labels `torch.cat(...).cpu().numpy().astype(bool)` as before. Predictions are appended in loader order by `_PredictionLoop._predict_step` (`self._predictions[dataloader_idx].append(move_data_to_device(predictions, cpu))`) and `trainer.predict(..., return_predictions=True)` returns that single list for one dataloader. Pure re-plumbing of already-final float32 values; `.astype(np.float32, copy=False)` on an fp32 array is a view.

### Loader gains pin_memory=True and persistent_workers=True via shared_dataloader_kwargs

- file: `src/every_query/data/conditional_multitask_datamodule.py` (lens: data-and-order, affects: none, expected: none / bitwise identical, confidence: high)

Old (predict_multitask.py build_dataloader): `DataLoader(dataset, batch_size=int(batch_size), shuffle=False, collate_fn=dataset.collate, num_workers=int(num_workers))`. New (_eval_dataloader): `DataLoader(dataset, shuffle=False, collate_fn=dataset.collate, **self.shared_dataloader_kwargs)`. The upstream meds_torchdata Datamodule.shared_dataloader_kwargs contains exactly: batch_size; num_workers and pin_memory when not None; prefetch_factor only when set AND num_workers>0; persistent_workers = explicit value, else True when num_workers>0. It never sets drop_last, worker_init_fn, generator, sampler or timeout. build_predict_datamodule passes `pin_memory=dm_cfg.get("pin_memory")` (True for the evaluation checkpoint) and num_workers=8, so the evaluation loader is now `{batch_size: 192, num_workers: 8, pin_memory: True, persistent_workers: True}` vs the old `{batch_size: 192, num_workers: 8}`. Mechanism check: pin_memory is a silent no-op for the batch (torch's pin_memory only pins Tensor / Mapping / Sequence / objects with a `.pin_memory` method; MultitaskEvalBatch is a dataclass with no such method, so the batch is returned unpinned); persistent_workers only matters across repeated iterations of the same loader, and trainer.predict iterates it once. drop_last stays at torch's default False on both sides, so the last partial batch is scored in both.

### Lightning rewraps the predict DataLoader (_IndexBatchSamplerWrapper, forced drop_last=False, worker_init_fn)

- file: `src/every_query/predict/predict_multitask.py` (lens: data-and-order, affects: none, expected: none / bitwise identical, confidence: high)

The new path scores through `trainer.predict(model, datamodule=datamodule, return_predictions=True)`. ### eval_config via dataclasses.replace re-runs __post_init__ but is value-identical to the old data_cfg

- file: `src/every_query/data/conditional_multitask_datamodule.py` (lens: data-and-order, affects: none, expected: none / bitwise identical, confidence: high)

### strip_delta_tokens, expected_vocab_size and max_windows forwarded with identical values and identical rejection rules
